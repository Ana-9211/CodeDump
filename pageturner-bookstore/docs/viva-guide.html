Rubric 1. ER diagram

The ER diagram (Chen notation)

In everyday terms: An ER diagram is the architect's floor plan: rooms (entities), doors between them (relationships), and what each room contains (attributes).

Open
  • docs/diagrams/er-chen-overview.png
Run live
  • Open docs/diagrams/er-chen-overview.png in the first tab, then er-chen-orders.png if asked for detail.
Say this (30 to 60 seconds)Open the overview. Rectangles are entities, diamonds are relationships, ellipses are attributes. Double rectangles are weak entities: a seller profile, an order item and a payment cannot exist without their owner, so each hangs off a double diamond. Many-to-many links, such as books and authors, are diamonds marked M and N with their own attributes (author_order), not junction tables. Category points at itself through the recursive diamond Parent Of. The purple dashed box is MongoDB: reviews and views are not part of the relational model and are linked only by book_id and user_id. Detailed diagrams per domain are in the same folder, and the notation key is in docs/relational-schema.md.
Likely examiner questions
Why is Order Item a weak entity?
It has no meaning without its order: it is deleted with the order (ON DELETE CASCADE) and is identified through it. The double rectangle and double diamond show that dependence.
Where are the foreign keys in a Chen diagram?
They are not attributes; they are the lines from an entity to a relationship diamond. They appear as columns only after mapping to tables, which docs/relational-schema.md lists.

Rubric 2. Relational schema

The relational schema and normalization

In everyday terms: Normalization is writing every fact on exactly one index card, so when something changes you fix one card.

Open
  • docs/relational-schema.md:49-74
  • docs/relational-schema.md:88-99
Run live
  • psql -d bookstore_dbms -c "\dt" (lists the 20 tables)
Say this (30 to 60 seconds)This is the ER diagram mapped to 20 tables. Each table lists its primary key, foreign keys and what is special: users to roles, seller_profiles as a 1:1 extension, book_authors, cart_items and wishlist_items as the M:N tables with composite keys, categories as a self-reference. Money is stored as integer paise, so there is no floating point drift. The normalization section shows each fact lives on one card: authors moved out of books, category names live only in categories. The documented exceptions are the price and address snapshots in orders and order_items, and the cached avg_rating.
Likely examiner questions
Is your schema in BCNF?
Every determinant in the main tables is a candidate key, so yes. The deliberate exceptions are snapshots (history must not change when a price changes) and the avg_rating cache, both documented.
Why integer paise instead of numeric?
Integers are exact and sum correctly with no rounding mode to think about; formatting to rupees happens only in the interface.

Rubric 3. DDL

DDL: tables, keys and constraints

In everyday terms: Constraints are the locks on the shop doors: it does not matter who holds the key to the front office, the stock room still will not open for the wrong person.

Open
  • db/postgres/01_schema.sql:98-127
  • db/postgres/01_schema.sql:82-90
Run live
  • psql -d bookstore_dbms -c "\d books"
  • npm run db:reset (rebuilds everything from these files; run npm run db:seed afterwards)
Say this (30 to 60 seconds)Open the books table. Identity primary key, foreign keys to the seller and the category with RESTRICT so nobody can delete a category that still has books. CHECK constraints guard the data itself: ISBN shape, price above zero, stock never negative, a fixed set of statuses. search_vector is a generated tsvector column, so full text search needs no application code. Now categories: parent_id points back at the same table, a CHECK stops a category being its own parent, and NULLS NOT DISTINCT makes root names unique too. The database refuses bad data even from a superuser.
Likely examiner questions
Why CHECK constraints when the app already validates?
The app is one writer among many (scripts, psql, future services). Constraints are the last line of defence and cost nothing.
What does ON DELETE RESTRICT on category_id protect?
It stops deleting a category that still has books or children, so no book is left without a genre.

Rubric 4. NoSQL creation

MongoDB: collections, validators and indexes

In everyday terms: A suggestion box next to the till: flexible notes in any amount, kept apart from the cash register that must balance to the paisa.

Open
  • src/lib/mongo.js:52-69
  • src/lib/mongo.js:96-127
Run live
  • npm run nosql:demo (creates, reads, updates and deletes reviews live and prints the indexes)
  • mongod is the Windows service MongoDB on 127.0.0.1:27017
Say this (30 to 60 seconds)Reviews and view events are documents, not rows, so they live in MongoDB. The reviews validator is a JSON Schema: bookId, userId, rating from 1 to 5, a body of up to 2000 characters, and helpfulBy as an array of voter ids. setupMongo is idempotent: it creates the collections, applies validators and builds three indexes on reviews, including a unique index on bookId plus userId so one person cannot review a book twice. book_views gets a TTL index so click events delete themselves after 30 days. If MongoDB is down the shop still works.
Likely examiner questions
Why did you choose MongoDB for reviews?
A review is one self-contained document with an array of voters, read as a whole, write-heavy and never joined inside a money transaction. The only link to PostgreSQL is the numeric ids.
What happens if a review document breaks the schema?
The validator (strict, action error) rejects it. The API validates first, so the user sees a clear 400 rather than a database error.

Rubric 5. Technology justification

Why these technologies

In everyday terms: Choosing the right container: a safe for money, a box for notes, and a shop front that serves both.

Open
  • docs/technology-justification.md:1-11
Run live
  • Open docs/technology-justification.md
Say this (30 to 60 seconds)One table, one real reason per choice. PostgreSQL for money, stock and identity because they need ACID transactions and row locks. MongoDB for reviews because they are documents. Next.js because the interface and the API route handlers live in one project next to the database driver. bcrypt plus a signed httpOnly cookie so the page scripts cannot read the session. Database level role based access so that even a bug in the web layer cannot leak another customer's order. Each row names the alternative we rejected.
Likely examiner questions
Why not MongoDB for everything?
Checkout needs several writes to succeed or fail together, with row locks on stock. Multi-document transactions exist, but relational constraints, triggers and RLS are what this project is about.
Why not a separate Express API?
Next.js route handlers give the same API shape with one deployable unit; the paths and roles are the same, and it is documented as a deviation.

Rubric 6. DML

DML: INSERT, UPDATE, DELETE, SELECT

In everyday terms: A rehearsal on a stage with the safety net up: every move is real, nothing is kept.

Open
  • db/postgres/queries/dml_examples.sql:1-41
Run live
  • psql -d bookstore_dbms -f db/postgres/queries/dml_examples.sql
  • In the open psql window you can also type: \i db/postgres/queries/dml_examples.sql
Say this (30 to 60 seconds)The whole script runs inside a transaction that ends in ROLLBACK, so I can run it any number of times and the shop never changes. INSERT a new author, a book and the many-to-many link, using RETURNING to show the generated ids. INSERT ... SELECT with ON CONFLICT is an upsert: add to cart or bump the quantity. UPDATE ... FROM with a join gives a 10 percent cut to the Portal Fantasy category. UPDATE with a subquery restocks nearly sold-out books. DELETE with a subquery clears the carts of suspended users. The last query shows the audit rows the triggers wrote during this very transaction.
Likely examiner questions
Why does the script end in ROLLBACK?
So the demo is repeatable and cannot damage the data. Everything inside is real SQL; the audit rows at the end prove the triggers fired.
What does ON CONFLICT DO UPDATE do?
It turns an insert that would break the (user_id, book_id) key into an update of the quantity, capped at 10 by LEAST, in one atomic statement.

Rubric 7. Nested, correlated, recursive and join queries

Subqueries, recursion and joins

In everyday terms: Walking a family tree: start with the oldest relatives, then keep asking who their children are until nobody is left.

Open
  • db/postgres/queries/advanced_queries.sql:7-26
  • db/postgres/queries/advanced_queries.sql:32-58
  • db/postgres/02_functions.sql:401-423
Run live
  • psql -d bookstore_dbms -f db/postgres/queries/advanced_queries.sql
Say this (30 to 60 seconds)Query 1 is nested: books priced above the average of their category. Queries 3 and 4 are correlated: the inner query refers to the outer row, so it runs again for each book, giving the most expensive book per category and the books nobody has ever ordered (NOT EXISTS). Query 5 is the recursive CTE: start at the root categories, then keep joining children to what was already found, building depth and a path such as Children's Fiction > Middle Grade > Animal Stories. The same logic is packaged as fn_category_tree, which the catalogue filter uses so that choosing Fantasy includes all its sub-genres. Query 6 shows inner and left joins, 7 a self join of categories to their parent.
Likely examiner questions
Correlated versus nested subquery?
A nested subquery is evaluated once; a correlated one refers to the outer row and is evaluated per row. Query 1 compares each book with the average of its own category, which is correlated by category_id.
Why recursion instead of a fixed three-level join?
The tree can be any depth. A recursive CTE walks it without knowing the depth, and the cycle guard is the CHECK that a category is never its own parent.

Rubric 8. Advanced SQL

Triggers, stored procedure, window function, views

In everyday terms: A trigger is a shop alarm that goes off whatever the person at the till tries.

Open
  • db/postgres/03_triggers.sql:73-86
  • db/postgres/03_triggers.sql:90-109
  • db/postgres/02_functions.sql:150-225
  • db/postgres/02_functions.sql:373-397
Run live
  • In psql, inside a transaction so nothing is kept: BEGIN; UPDATE order_items SET fulfilment_status = 'Delivered' WHERE order_item_id = (SELECT min(order_item_id) FROM order_items WHERE fulfilment_status = 'Placed'); ROLLBACK; (the error is: illegal status change Placed -> Delivered)
Say this (30 to 60 seconds)Two triggers. fn_order_item_take_stock fires after every order line is inserted: it subtracts the stock and writes a stock_movements ledger row, so stock can never be forgotten. fn_guard_item_status only allows Placed to Packed to Shipped to Delivered, and Cancelled early; any other jump raises an error. sp_place_order is the checkout as one transaction: it locks the book rows with FOR UPDATE, checks stock and status, copies the address and prices into the order as a snapshot, inserts the lines, the payment, and clears the cart. If anything fails, everything rolls back. fn_sales_report uses SUM(...) OVER (ORDER BY day), a window function, for the running revenue line on the dashboards.
Likely examiner questions
Two customers buy the last copy at the same instant. What happens?
sp_place_order takes row locks in a fixed order with FOR UPDATE. The second transaction waits, then sees stock 0 and raises an error that rolls it back completely. A test races them.
Why a trigger for stock instead of application code?
The rule then holds for every code path, including psql. A trigger is a door that locks itself; application code is a sign asking people to close it.

MongoDB read, update and delete

In everyday terms: Index cards in a box: look one up, correct it in place, or tear it up, and the tally on the lid is redone each time.

Open
  • src/lib/reviews.js:40-55
  • src/lib/reviews.js:109-121
  • src/lib/reviews.js:123-130
  • src/lib/reviews.js:133-147
Run live

  • In the app: log in as customer2@bookstore.test, open a book you bought (for example The Princess Bride), edit your review.
Say this (30 to 60 seconds)Read: the star summary is one aggregation pipeline, match the book, group by rating, and the list uses find with sort, skip and limit. Update: findOneAndUpdate with $set, filtered by both the review id and the user id so you can only edit your own. Likely examiner questions
How do you stop someone editing another person's review?
The update filter is { _id, userId }. If the user id does not match, nothing is updated and the API returns 404.
Why mirror the rating into PostgreSQL?
Sorting the whole shelf by rating needs one indexed column. Asking MongoDB for every book's average on every page load would be slow and would make a Mongo outage break the shelf.

Rubric 11. Backend and database integration

API routes talking to PostgreSQL

In everyday terms: The route handler is a receptionist: it checks your badge, then lets the database decide which rooms you may enter.

Open
  • src/lib/db.js:50-67
  • src/app/api/books/route.js:16-45
  • src/app/api/orders/route.js:18-39
Run live
  • Log in as customer1@bookstore.test, add a book, check out with card 4242 4242 4242 4242, expiry 12/39, CVV 123. A declined test card is 4000 0000 0000 0002.
Say this (30 to 60 seconds)withRole is the heart of the integration: every request opens a transaction, runs SET LOCAL ROLE to the user's database role and sets app.user_id, so GRANTs and row level security apply to that request. The books route builds its filters with bound parameters only; the sort column comes from a fixed whitelist, never from the request. The checkout route charges the simulated payment gateway first, calls sp_place_order, and if the order fails it refunds the charge, so money is never taken without an order. Card numbers are validated by the gateway adapter and never reach the database; only a masked label is stored.
Likely examiner questions
How do you stop SQL injection?
Every value is a bound parameter ($1, $2). The only interpolated pieces, the sort column and the role name, come from fixed whitelists.
What if the payment succeeds but the order fails?
The catch block calls refund(reference). Then the original error goes to the user.

Rubric 12. Authentication and RBAC

Login, sessions and three layers of access control

In everyday terms: A hotel key card: GRANT is the floor you can reach, row level security is the room, and the front desk checks your ID for anything special.

Open
  • src/lib/auth.js:21-31
  • src/lib/http.js:9-21
  • db/postgres/05_security.sql:39-61
  • db/postgres/05_security.sql:128-132
Run live
  • psql -d bookstore_dbms -f db/postgres/queries/rbac_demo.sql (the permission denied lines are intentional)
  • Log in as customer1, seller1 and admin@bookstore.test, password Passw0rd!
Say this (30 to 60 seconds)Layer one is GRANT: which tables and even which columns a role may touch. A customer cannot read password_hash because the column grant leaves it out; a seller can update only the fulfilment_status column of an order line. Layer two is row level security: a customer sees only rows where user_id equals app_user_id(); a seller sees orders only if one of their books is in them. Layer three is the stored procedures that start with fn_require_role. Passwords are bcrypt hashes; the session is a signed JWT in an httpOnly cookie that only proves who you are, and what you may do is decided by PostgreSQL. The CSRF guard rejects a foreign Origin and any body that is not JSON.
Likely examiner questions
Why SET LOCAL and not SET?
SET LOCAL lasts only for the current transaction, so a pooled connection cannot carry one user's role into the next request.
What is SECURITY DEFINER and is it dangerous?
The function runs with its owner's privileges so it can write tables the caller cannot. It is safe here because each one starts with fn_require_role, fixes search_path and EXECUTE is not public.

What is original in this project

Honest limits
  • Payments are simulated. A test gateway adapter validates card shape and returns a reference; no real money moves and no card data is stored.
  • E-mail is simulated. Messages go to a console transport and a database outbox; no SMTP server is used.
  • Cover images depend on the images that are supplied. Until they are applied every book shows a "cover pending" tile; no artwork was invented.
  • Seed ISBNs are synthetic: they have a valid check digit but are not the real ISBNs of those books. Titles and authors are real.
  • Not deployed: it runs locally on http://localhost:3000, so HTTPS and the 99 percent availability target are not demonstrated.
  • Running npm test wipes the database and Mongo collections. Re-run npm run db:reset and npm run db:seed afterwards.
30-second pitch. One bookstore, two databases chosen on purpose: PostgreSQL for money, stock and identity (transactions, triggers, procedures, Row Level Security so roles are enforced by the database itself) and MongoDB for flexible, write-heavy reviews and view events. Next.js gives the interface and the API: an illustrated bookshelf where a book opens in place. Everything is tested: 129 automated tests including a concurrency race for the last copy.
